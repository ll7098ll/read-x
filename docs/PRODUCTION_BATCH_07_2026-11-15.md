# 일곱 번째 개발 묶음 — 교사·운영자 추가 인증과 안전한 초기 등록

<!-- readx-document-context -->
> 작성 당시의 설계·조사·구현 기록입니다. 현재 기능과 운영 상태는 최신 현황을 우선합니다. [문서 목차](README.md) · [최신 현황](PROJECT_STATUS.md)


2026년 11월 15일. 직접 운영하는 학원의 개인정보 접근 통제를 보완했다. 기본 서버의 교사·원장은 비밀번호와 인증앱을 모두 확인해야 학생 기록·수업·평가·배치 진단·운영 화면에 접근한다. 공개 Sites는 계속 가상 자료를 사용하는 정적 체험판이다. 이 구현은 실제 개인정보 운영 승인이나 법률·보안 심사의 완료가 아니다.

## 구현한 동작

- 인증앱 등록·코드 확인·변경·일회용 복구 코드 재발급·복구 후 재등록을 실제 HTTP API와 화면에 연결했다. 교사·원장은 추가 인증을 해제할 수 없다. 학생·보호자는 선택적으로 사용할 수 있다. 새 교사는 초기 비밀번호를 먼저 본인 비밀번호로 바꾼다.
- TOTP는 SHA-1, 6자리, 30초 간격이다. 현재 시각의 앞뒤 한 구간까지 허용하며 사용한 카운터 이하는 거부한다. 새 권한 작업에서 방금 사용한 코드를 다시 쓸 수 없으므로 다음 코드를 입력한다. 설정키와 복구 코드는 생성 직후 한 번만 화면에 보이고 서버 조회에서는 반환하지 않는다. 외부 QR 생성 서비스로 설정키를 보내지 않는다.
- 인증앱 등록 대기 10분, 로그인 추가 인증 대기 5분, 완료한 추가 인증 세션 8시간, 복구 후 재등록 세션 5분이다. 유휴 시간 기준 자동 잠금 기능을 구현한 것은 아니다. 다른 사람의 비밀번호 입력만으로 기존 인증 완료 기기를 강제 종료할 수 없고, 인증 완료 후 기존의 한 기기 편집 정책을 적용한다.
- 비밀번호만 확인한 세션은 연결 자녀·반 메타데이터도 받지 않는다. 읽기·평가·진단·코스·리포트·명단·키 발급에 공통 인증 경계를 적용한다. 권한은 서버의 계정·기관 정책으로 판단하며 요청 본문의 역할·정책 변경으로 우회할 수 없다.
- 교사 생성, 담당 반·원장 권한·교사 활성 변경, 학생 반 이동, 비밀번호 복구 발급, 보호자 연결·확인·해제, 안내문 게시에는 원장의 현재 비밀번호와 새 인증앱 코드를 추가로 확인한다. 일반 비밀번호 변경·인증앱 변경·복구 코드 재발급에도 현재 자격 증명이 필요하다. 비밀번호 복구로 기존 MFA가 제거되지 않는다.
- 추가 인증 실패 횟수는 DB에 남는다. 15분 구간에서 8회 실패하면 15분간 제한한다. 오류 응답에도 횟수를 저장하고 재시작 후 유지한다. 코드는 변경 기록에 남기지 않는다. 기존 첫 비밀번호 단계의 메모리 기반 요청 제한은 별도 운영 개선 대상이다.

## 운영자 등록·복구 절차

운영 모드(`READX_RUNTIME=production`)에서는 계정이 없는 DB라도 웹 `/setup`을 열지 않으며, 강제로 활성화하려 하면 시작을 거부한다. 로컬 프록시를 통과한 요청을 서버 내부 등록으로 취급하지 않는다. 개발용 웹 초기 설정도 루프백 연결과 localhost Host를 함께 요구한다.

서버 관리자가 신뢰할 수 있는 터미널에서 `node server/bootstrap-owner.mjs --db 운영DB절대경로`를 실행한다. 도구의 입력 대기 상태에서 이름·아이디·비밀번호·반 이름의 JSON 한 줄을 입력한다. 입력을 명령 인수나 셸 기록에 쓰지 않는다. 도구는 stdin 입력을 화면에 에코하지 않으며, 8KiB를 넘는 입력·잘못된 형식·다른 프로젝트 DB·계정이 이미 있는 DB를 거부한다. 첫 운영자 한 명만 만들며 비밀번호는 기존 scrypt 형식으로 해시한다. 첫 로그인 후 인증앱 등록을 마쳐야 학생 기록을 볼 수 있다. 실제 터미널·서버 권한과 녹화·세션 로깅 정책 검토는 별도로 필요하다.

인증앱을 잃은 경우 비밀번호와 미사용 복구 코드 한 개를 확인하고, 기존 세션·기기 초안 키와 이전 인증앱을 무효화한다. 새 인증앱 등록 전에는 학생 정보를 열지 않는다. 새 등록이 완료되면 이전 복구 코드 세트도 모두 무효화한다.

앱과 복구 코드를 모두 잃었다면 서버 관리자가 별도 본인 확인 절차를 거친 뒤 `server/recover-mfa.mjs`를 사용한다. 기존 DB·계정·사유·확인 문서 참조와 `--verified-identity`를 요구한다. 기존 활성 MFA 계정만 처리하고 계정이나 원장 권한을 만들지 않는다. 15분 유효한 일회용 토큰은 해시만 저장하며 한 번 출력한다. 비밀번호 확인 뒤 이 토큰을 사용해도 제한된 재등록 세션만 발급한다. 명령 플래그가 실제 본인 확인을 대신하지 않으며, 실제 확인 담당·기준·안전한 전달 수단은 운영 책임자가 정해야 한다.

로컬 초기 등록·비밀번호 복구·MFA 복구 기록은 계정 본인이 행동한 것으로 오인하지 않도록 `local-server-admin` 행위자와 대상·기관을 구분했다. 전체 열람·출력 접속기록과 별도 보관·위변조 방지는 다음 개발 범위이며 아직 구현 완료가 아니다.

## 키와 기기 초안

MFA 설정키는 계정·기관을 인증 부가 데이터로 묶은 AES-256-GCM으로 암호화해 DB에 저장한다. 운영 모드에서는 별도 `READX_MFA_KEYS` 구성이 없으면 시작하지 않는다. 형식은 `{ "activeId": "키식별자", "keys": { "키식별자": "별도 생성한 32바이트 키의 Base64" } }`이며 실제 키를 소스·배포 문서·공개 Sites에 넣지 않는다. 구성이 잘못되거나 기존 암호문을 열 수 없으면 새 키를 임의 생성해 덮지 않고 중단한다.

키 교체 시 새 활성 키와 필요한 이전 키를 함께 보유하면 기존 인증앱 코드 확인에 성공할 때 새 키로 다시 암호화한다. 이전 키 삭제 전 모든 저장본·백업의 교체와 복원 가능 여부를 확인해야 한다. 일괄 재암호화 도구·운영 키 보관소·분리 권한·키 유실 복구 훈련은 남아 있다. 비운영 영속 DB는 별도 `.mfa-keys.json`을 개발 편의로 생성한다. POSIX mode 600 설정이 Windows ACL 보안을 보장하지 않으므로 운영 수단으로 사용하지 않는다. DB·키 파일은 Git 및 Sites 동기화 대상에서 제외한다.

이번 묶음은 [여섯 번째 기록](PRODUCTION_BATCH_06_2026-11-14.md)의 자동 재인증 동작을 보완한다. 세션 만료·추가 인증 대기에서는 메모리의 기기 초안 키와 기존 접근 핸들을 해제하고 유효한 암호문을 남겨 본인 재인증 후 복구한다. 명시적 로그아웃·계정 교체·비밀번호/MFA 변경·복구에서는 기기 암호문도 정리한다. 늦게 도착한 이전 응답은 새 세션을 덮지 못한다. 닫힌 브라우저에서 정확히 12시간 후 물리 삭제되는 것은 아니며, 만료된 초안은 이후 접근·정리 때 제거하고 복구하지 않는다. 같은 출처의 악성 스크립트, 잠금 해제된 기기, OS 기록, 서버 전체 암호화·키 관리의 문제가 모두 해결된 것은 아니다.

## 검증과 남은 범위

운영 원본 전체 빌드에서 UI·도메인 80개와 서버·운영 61개, 합계 141개 검사가 통과했다. 비공개 평가 자료의 운영 번들 비포함, HTML/CSS 외부 자동 리소스 검사도 통과했다. 최종 초기 등록·복구 기록 보완 후 관련 서버 20개 검사를 다시 통과했다. 결과는 `output/mfa-final-build-2026-11-15.log`, `output/mfa-bootstrap-recovery-2026-11-15.log`에 있다. 동시 진행 중인 배치·코스 구현도 기존 소스를 보존하여 검사했다.

추가 인증 서버 검사는 RFC 6238의 18개 알고리즘 벡터, 시각 오차·재사용, 계정 간 암호문 이동·키 교체, 인증 전 경계, 세션·등록 쿠키 결합·만료, 복구 재사용·강제 재등록, 실패 누적·재시작, 비밀번호 복구 우회, 비공개 메타데이터, 운영 웹 초기 설정 차단, 로컬 등록 후 로그인·접근 차단을 포함한다. 자료는 모두 가상 계정이다.

사용자가 중단한 컴퓨터 제어를 재개하지 않았다. 실제 휴대전화 인증앱과 데스크톱·모바일 브라우저의 전체 조작 검증, 접근성·부하·현장 점검은 아직 수행하지 않았다. 인증앱 코드 방식은 피싱 저항 인증을 뜻하지 않는다. 패스키·중앙 비밀 관리·DB와 백업 암호화·접속기록 보호·개인정보 권리 처리·파기·국내 운영 계약·실제 방침·전 학년 정식 평가·콘텐츠 검수 등 남은 작업을 계속한다. 운영 준비 23개 통제는 모두 검토 대기 상태를 유지하며 `start:production` 승인을 만들지 않았다.

공개 사이트는 다음 배포의 서버 반환 버전·커밋·성공 상태를 별도 배포 기록에 남긴다. 정적 체험판에서 MFA 서버가 실행되는 것으로 표시하지 않는다.

기술 기준: [RFC 6238](https://www.rfc-editor.org/rfc/rfc6238.txt), [Google Authenticator Key URI 형식](https://github.com/google/google-authenticator/wiki/Key-Uri-Format), [OWASP 다중 인증 지침](https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html). 이 자료는 기술 설계 근거이며 법률 적합성 확인서가 아니다.
