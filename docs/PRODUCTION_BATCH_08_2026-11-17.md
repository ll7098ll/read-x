## 서버 경계와 기록 범위

`server/exam-service.mjs`에서 실제 HTTP 요청을 공통 처리한다. 정상 응답은 접속기록과 업무 자료를 같은 SQLite 트랜잭션에 저장한 뒤 전달한다. 기록 저장이 실패하면 업무 변경을 취소하고 성공·개인정보 응답을 보내지 않는다. 권한·MFA·요청 형식 등의 거부도 별도 트랜잭션에 기록하며 거부로 취소된 업무 변경을 저장하지 않는다. 실패 기록도 저장할 수 없으면 서버 실패로 처리한다.

기록에는 서버 생성 요청 ID, 시각, 기관·접속 계정 ID와 역할, 접속 IP와 판단 근거, 표준화한 업무 경로, 대상 계정 ID, 처리 상태, 응답 바이트 수, 내보내기 목적·참조를 둔다. 대상은 실제 반환한 명단·수행·공개 기록과 서버가 확인한 요청 대상에서 수집한다. 임의 요청의 다른 기관 ID를 본 기관의 처리 대상에 넣지 않는다. 이름·연락처·학생 글·답안·상담 원문·비밀번호·인증앱 키·복구 코드·쿠키·원본 URL·쿼리를 접속기록에 복사하지 않는다. 경로의 객체 ID는 표준 자리표시자로 바꾸며 허용된 업무 밖의 요청은 `unknown`으로 기록한다.

올바른 아이디에 대한 로그인 실패는 해당 기관에 기록하되 인증된 행위자로 오인하지 않도록 접속 계정은 미인증으로 두고 시도 대상 ID를 별도로 둔다. 알 수 없는 계정의 실패는 시스템 범위 기록이며 학원 운영 화면에서 임의 기관에 배분하지 않는다.

기본 접속지는 소켓 IP다. `READX_TRUSTED_PROXY_IPS`에 정확한 IP 목록을 설정한 경우에만 해당 프록시의 `X-Forwarded-For`를 확인하고 오른쪽부터 신뢰 경계를 따라 실제 접속지를 판단한다. 일반 클라이언트가 보낸 헤더와 잘못된 형식은 접속지 근거로 사용하지 않는다. 운영 프록시의 헤더 덮어쓰기·외부 직접 접근 차단·실제 네트워크 검증은 별도로 필요하다.

## 다운로드·인쇄와 원장 화면

일반 리포트 조회 응답에서 미리 생성한 CSV를 제거했다. CSV·인쇄 준비 버튼은 서버에서 현재 조회 범위와 권한·보호자 공개 상태를 다시 확인한다. 교사는 목적을 선택하고, 권리 요청·사고 조사는 문서 참조도 입력한다. 학생 본인·보호자의 공개 자녀 결과는 본인·보호자 접근 목적으로 구분한다. 보호자 연결 철회나 공개 회수 뒤에는 이전 화면을 열어 두었더라도 새 인쇄 준비·파일 요청에 현재 권한을 적용한다. 모의고사 인쇄도 최신 서버 공개본으로 준비한다.

원장 계정의 학원 운영 화면에 접속기록 패널을 추가했다. 기간(한 번에 90일 이내), 업무, 처리 결과, 접속 계정·처리 대상 ID로 조회한다. 조회는 100건씩 번호 기준으로 이동한다. 점검 파일은 최대 1,000건씩 다음 위치를 명시해 이어서 받을 수 있다. 자신의 기관만 조회하며 본문에 다른 기관을 지정해 범위를 넓힐 수 없다. 다운로드와 점검 기록 자체도 감사 대상이다. 점검 결과는 확인한 번호 범위·결과·문서 참조를 새 기록으로 추가한다. 기존 기록을 수정하는 기능은 없다.

점검 자료·기준점 다운로드와 점검 결과 등록에는 기본 운영 원장의 현재 비밀번호와 새 인증앱 코드를 다시 확인한다. 접속기록 조회도 기존 MFA 접근 경계 안에 있다. 일반 교사·학생·보호자는 원장 접속기록 화면·API에 접근할 수 없다.

앱의 버튼을 통한 파일 전달·인쇄 준비 요청을 기록하는 것이며, 실제 종이 출력 완료·브라우저 메뉴의 인쇄·스크린샷·외부 파일의 재전달·파기까지 증명하거나 차단하지 않는다. 출력물·파일의 운영 규정과 단말 통제가 여전히 필요하다.

## 변경 탐지와 키·별도 기준점

`access_log`와 대상 색인은 기존 JSON 변경 이력과 분리한 추가 전용 표다. 일반 SQL 수정·삭제는 트리거로 거부한다. 각 행은 순번·이전 서명·본문·키 식별자를 HMAC-SHA256으로 연결한다. 시퀀스·서명·대상 색인을 검사하며 시작 시 전체 검사, 요청마다 마지막 기준점 검사, 원장 점검·자료 조회 시 전체 검사를 수행한다. 키를 가진 정당한 로컬 관리 도구가 새 행을 추가한 경우에도 앞선 기준점을 검증한 뒤 이어받는다. 로컬 첫 운영자 등록·비밀번호 복구·MFA 복구도 업무와 같은 트랜잭션에 접속기록을 남긴다. 복구 토큰을 접속기록에 남기지 않는다.

운영 모드는 별도 `READX_AUDIT_KEYS` 없이는 시작하지 않는다. 형식은 MFA 키 구성과 동일한 `{activeId,keys}` 구조지만 독립적인 32바이트 검증 키를 생성·보관해야 한다. 검증에 필요한 이전 키를 유지하면 교체 후 이전 기록과 새 기록을 함께 검증한다. 비운영 모드의 `.audit-keys.json`은 개발 편의용이다. Windows ACL·서버 키 보관소·담당자 분리·키 복구 운영을 검증한 것으로 간주하지 않는다. Git과 공개 사이트 동기화에서 DB·환경 파일·MFA 및 감사 키 파일을 제외한다.

기준점 파일은 DB 식별자·마지막 순번·서명과 자체 서명을 담는다. 원장 화면에서 받은 뒤 원본 서버·DB와 분리된 변경 방지 저장소에 보관해야 한다. 신뢰할 수 있는 서버 터미널의 `node server/verify-access-log.mjs --db 기존DB --checkpoint 별도보관기준점`으로 읽기 전용 검사를 수행한다. 필요한 검증 키는 환경의 안전한 경로로 공급한다. 기준점은 마지막 다운로드 이전의 로그를 확인하며, 다운로드 요청 자체 등 뒤의 새 행은 다음 기준점에 들어간다.

서명 키를 모르는 DB 변경은 탐지할 수 있지만, DB 관리자에게 트리거 제거를 절대 불가능하게 만드는 수단은 아니다. 서버 재시작 전에 전체 기록을 삭제·이전 DB로 복원하는 행위는 별도 보관 기준점과 대조해야 강하게 탐지할 수 있다. 키까지 장악한 공격, 로그·키·백업의 동시 분실, 외부 보관소 미운영은 이 구현만으로 해결되지 않는다. 별도 중앙 로그 수집·변경 방지 스토리지·정기 점검·경보·복구 훈련은 남아 있다.

## 검증·운영 준비 상태

HTTP 통합 검사에 조회·변경·인증·거부·다운로드 분리, 학생 대상 추적, 비밀·원문 비포함, 거부 이력의 영속 저장, 권한·기관 분리, 보호자 공개 회수 후 인쇄 거부, 기록 장애 시 자료 변경 취소, 페이지 이동·점검, 프록시 위조, 키 교체·키 유실·본문/색인 변경·기준점 이전 복원 탐지와 읽기 전용 CLI 검사를 추가했다. 가상 계정과 임시 DB만 사용한다. 최종 운영 원본 전체 빌드에서 UI·도메인 80개와 서버·운영 78개, 합계 158개 검사가 통과했다. 비공개 평가 자료의 운영 번들 비포함과 HTML/CSS 외부 자동 리소스 검사도 통과했다. `output/access-final-build-2026-11-17.log`에 증거를 남겼다. 동시 진행된 전 학년 진단·코스 확장의 기존 소스를 보존해 함께 검사했다. 실제 브라우저·인증앱·학원 단말 조작 검증은 수행하지 않았다. 공개 사이트는 검증한 정적 체험판 산출물로 후속 배포하고 서버가 반환한 버전과 배포 결과를 별도 기록한다.

기존 `s.audit`의 과거 변경 이력을 새로 서명한 과거 접속기록으로 만들어내지 않았다. 새 코드 실행 이전의 조회 이력은 복원된 것으로 주장하지 않는다. 현재 추가 전용 접속기록의 보존·안전한 아카이브·만료 파기 절차, 자료별 보유기간, 개인정보 권리 요청·파기, 키·백업·국내 업체·실제 방침, 현장·브라우저·침투 검증은 미완료다. 23개 운영 준비 통제는 `open`으로 유지한다.

설계 시 현행 [개인정보의 안전성 확보조치 기준(2026년 7월 1일 시행)](https://www.law.go.kr/LSW/admRulInfoR.do?admRulSeq=2100000281400)의 접속기록 구성, 제8조 보관·점검·보호, 제12조 출력 용도·최소화 기준을 확인했다. 법적 보관기간의 적용은 실제 처리 규모·유형·사업자와 운영 검토로 확정해야 하며, 코드의 추가 전용 보관을 법정 파기·보존 절차의 완성으로 보지 않는다. 기록 보관과 다운로드 점검 주기·방법·사후 조치는 실제 내부 운영 기준으로 정하고 이행해야 한다.
