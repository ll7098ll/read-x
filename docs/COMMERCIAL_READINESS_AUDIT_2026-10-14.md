### A01 정식 빌드 실패

**P0 · 빌드로 확인.** `webapp/src/services/firebaseDbService.ts:198`의 `ReadingHabitProfile`, 207행의 `BeforeAfterMetrics`를 가져오지 않아 TypeScript 검사에서 실패한다. Vite 개발 서버가 열리는 것과 정식 빌드가 통과하는 것은 다르다.

### A04 기관과 학생을 구분하는 서버 권한 체계 부재

**P0 · 코드 구조로 확인.** 역할은 로컬 상태의 탭 전환이며 Firebase SDK, 인증 초기화, 실제 DB 읽기·쓰기·동기화 호출이 없다. `firebaseDbService.ts`의 환경변수 설정은 실제 연결을 수행하지 않는다.

저장된 `firestore.rules`를 그대로 배포할 경우 인증된 사용자 누구나 학생 프로필과 응시 기록을 읽고, 과제를 읽고 쓸 수 있다. 학생·기관 소속을 확인하지 않고 교사 역할에 전역 쓰기를 허용한다. **현재 운영 서버에서 실제 정보가 유출되었다는 의미는 아니며, 이 규칙으로 운영을 시작하면 안 된다는 결론**이다.

조치: 기관·학급·학생·보호자 관계를 모델링하고 서버에서 권한을 검증한다. 학원 원장과 플랫폼 콘텐츠 편집자의 권한을 분리한다. A기관 사용자가 B기관의 모든 관련 문서에 접근하지 못하는 테스트를 통과해야 한다. Firestore에서는 인증 정보와 문서 데이터를 이용한 접근 조건을 명시하고 에뮬레이터로 규칙을 검증할 수 있다. [Firebase 접근 조건](https://firebase.google.com/docs/firestore/security/rules-conditions), [규칙 테스트](https://firebase.google.com/docs/rules/unit-tests).

### A05 과제 배정과 실제 학습 완료가 이어지지 않음

**P0 · 이벤트 경로로 확인.** `StudentAssignment`에는 학생 ID·기관 ID가 없다. 교사는 학생 이름을 과제 제목에 넣지만 저장소의 과제 배열은 하나다. 학생의 실제 풀이 완료와 과제 제출을 연결하는 세션 ID도 없다. 과제함의 ‘제출 완료 처리’는 풀이 없이 92점으로 완료 처리한다.

조치: `assignmentId + studentId + lessonVersionId + sessionId`로 배정부터 제출까지 연결한다. 완료 조건은 활동 수행 여부로 판정하며, 서버 접수 전에는 ‘제출 중’, 접수 후에는 ‘제출 완료’를 표시한다. 교사가 같은 기관의 다른 학생에게 배정한 과제는 보이지 않아야 한다.

근거: `types/courseware.ts:476`, `TeacherJourneyHub.tsx:24`, `StudentJourneyHub.tsx:35`, `StudentJourneyHub.tsx:54`, `store/useCoursewareStore.ts:429`.

### A06 진단과 성장 수치가 실제 학습의 근거가 아님

**P0 · 산출 코드로 확인.** 학부모의 6개 영역 점수와 850→940 성장 추이, 교사 성장 통계가 고정 값이다. 실시간 교실은 난수와 타이머로 움직인다. 상담 보고서 영역 점수는 대표 학생 총점에 상수를 더하거나 빼서 만든다. 교사 코멘트도 자동 고정 문장이 포함된다.

CAT는 모든 학년에 같은 문항 묶음을 사용하고 정답 개수만으로 고정 지수를 부여한다. 처방 적용 시 지수를 12로 나눈 값을 점수에 더하므로 초기 61점에서 전부 틀려도 `61 + floor(690/12)`가 100점 상한에 도달한다. 측정된 문해력 성장으로 해석할 수 없다. 문장 복잡도 `KReaD` 또한 생성기에서 학년별 상수로 설정된다.

조치: 시연 수치와 실제 기록을 분리한다. 초기 제품은 문항별 첫 시도 정답, 근거 선택, 도움 수준, 자기 설명, 교사 관찰을 보여준다. 표준화 근거가 확보되기 전까지 백분위·수능 등급·공인 독서지수로 표시하지 않는다. ‘관찰 부족’ 상태가 필요하다.

### A09 기존 검증기가 화면 오류와 교육적 오류를 놓침

### A10 저장과 오류 복구가 학습 기록을 보장하지 않음

조치: 서버 영속화와 학생별 로컬 초안, 날짜를 포함한 타임스탬프, 재시도 큐, 충돌 정책, 로그아웃 시 잔여 개인정보 처리, 기록을 지우지 않는 복구 경로를 설계한다. 브라우저 새로고침과 다른 기기에서 이어하기를 실제 검증한다.

근거: `store/useCoursewareStore.ts:332`, `store/useCoursewareStore.ts:468`, `AcademySeatBillingCard.tsx:40`, `common/ErrorBoundary.tsx:29`.

## 콘텐츠와 UI 품질 문제

### A11 콘텐츠 검수와 출판 근거

**P1.** 공통기초 24개는 정답을 `②`로 저장하지만 선택지는 `② 꽃이`처럼 전체 문자열이다. 이전 공통기초 UI의 문자열 동등 비교로는 정답을 맞힐 수 없다. 현재 학생 여정에서 이 화면이 연결되지 않는 문제와 별개의 데이터 결함이다.

5학년은 객관식 33개 중 30개, 6학년은 32개 중 30개가 첫 번째 선지를 정답으로 둔다. 문항별 정답 순서의 편중을 점검하고, 순서를 섞을 경우 응시 당시 순서를 함께 저장해야 한다. 14개 ‘오답 공식 미기재’는 부정 발문에서 타당한 진술을 오답으로 취급하는 사례도 있으므로 자동으로 잘못된 문항이라고 판정하지 않는다.

96개 슬롯의 최상위 스키마에는 출처·이용허락·검수자 필드가 없다. 이것만으로 권리 침해라고 단정할 수는 없지만, 판매 콘텐츠의 근거와 게시 승인을 추적할 수 없다. 원천 교과서의 기출간 문학 작품 후보를 다른 장르 확장에 이용할 경우 별도 권리 확인이 필요하다.

생성기는 기본 상태를 `published`로 만든다. 교과 성취기준 일치, 어휘 난도, 설명 구조, 사실 정확성, 정답 근거와 복수정답 가능성을 편집 검수한 뒤 게시해야 한다. `research/courseware_track2_passage_complexity_vocab_standards.md`에는 다른 위계 파일의 잘린 도구 출력이 들어 있어 완성된 난도 연구 문서로 사용할 수 없다.

### A12 브랜드와 사용자 언어의 불일치

**P1.** 기존 CI 문서는 Rx 심볼과 따뜻한 종이색·네이비 체계를 정의하지만 앱 헤더는 역할마다 색이 다른 `RX` 상자를 쓴다. 영문 역할 라벨, 수능·6D·D1~D6·슬롯·TEI·온디바이스 비용 표현이 학생과 학부모 화면에도 반복된다. 상품이 약속하는 학습 변화보다 구현 방식과 평가 권위가 앞에 나온다.

조치: 기존 명칭과 심볼을 기본 자산으로 삼아 한 가지 브랜드 체계로 정리한다. 학생은 ‘단서 찾기·생각 연결하기·내 말로 설명하기’, 교사는 ‘관찰 근거·지도할 학생·다음 수업’, 원장은 ‘반 운영·이용 현황·상담 자료’를 먼저 보게 한다. 공인 평가·기관 연계로 오해할 수 있는 문구와 임의 경력은 사용하지 않는다.

### A13 반응형과 접근성

**P1.** 390px 학부모 화면에서 탭 이름과 헤더가 여러 줄로 좁게 분절된다. 짧게 확인해야 할 화면이 긴 기술 설명과 큰 카드 여백으로 늘어난다. 학생 화면은 터치보다는 마우스 텍스트 선택에 기대는 부분이 있고, 구조도에는 클릭 가능한 `div`가 있다. 소스의 `aria-*` 속성 검색 결과는 0건이지만, 이것만으로 모든 네이티브 버튼이 접근 불가능하다는 뜻은 아니다.

조치: 부모 모바일, 학생 태블릿, 교사 데스크톱을 각각의 주요 환경으로 설계한다. 접근성 검증에는 키보드 동작, 초점, 대화상자, 색 이외의 상태 표기, 글자 확대, 모션 감소, 터치 대체 조작을 포함한다. WCAG 2.2 AA를 개발 목표로 삼되 별도 검증 없이 준수 인증처럼 표현하지 않는다. [W3C WCAG 빠른 참조](https://www.w3.org/WAI/WCAG22/quickref/).

### A14 운영 보안과 배포

**P1.** 앱에서 원시 HTML 삽입 위치가 19곳 검색된다. 현재 정적 데이터 자체가 공격이라는 뜻은 아니지만 향후 CMS 입력을 공유하면 저장형 스크립트 삽입 위험이 생긴다. 구조화된 콘텐츠 노드 또는 허용 목록 기반 정제가 필요하다.

전체 데이터 2,440,859바이트를 정적 import하며, Vite 설정은 단일 HTML 번들이다. 정답·해설·시연 명단도 함께 전달된다. 학습용 즉시 피드백과 평가용 응답의 요구를 분리하고, 기관 권한과 게시 범위에 맞춰 필요한 콘텐츠만 불러와야 한다.

npm 감사의 8개 항목은 개발 도구 계열이며 운영 의존성 감사는 0건이다. 실제 공격 가능성은 사용 경로에 따라 다르므로 운영 유출로 확대 해석하지 않는다. 자동 강제 업그레이드 대신 검증된 버전 조합으로 갱신하고 회귀 검사한다. 저장된 감사 결과의 근거는 [braces 권고](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm), [selector parser 권고](https://github.com/advisories/GHSA-rj75-hqrm-r3gf)다.

### A15 파일과 개발 공정의 정리

**P1 또는 P2.** 현재 작업 폴더는 Git 저장소가 아니다. 패키지에는 dev·build·preview 명령만 있고 자동 테스트·린트·배포 파이프라인이 없다. 루트와 docs의 주요 기획 문서 6쌍은 동일한 복사본이며, 두 HTML 프로토타입도 내용이 같다.

`TopGlobalNav`, `StudentPortalDashboard`, `ParentXRayReportView`, `TeacherClassMatrixView`는 현재 앱 import 그래프에 없다. 유용한 기존 기능을 회수할지, 이전 시안으로 보관할지 결정해야 한다. 삭제부터 할 필요는 없다.

일부 생성기는 이전 `courseware/` 경로나 개인 기기의 외부 디렉터리를 참조한다. `build_commercial_dataset.py`는 마스터 파일을 재생성하고 후속 컴파일러는 그 파일을 다시 읽어 합친다. 재생성 순서와 단일 원천을 정하지 않으면 기존 132슬롯 데이터를 덮어쓰거나 순환 의존을 만들 수 있다.
