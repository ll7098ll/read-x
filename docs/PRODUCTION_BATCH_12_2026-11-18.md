## DB와 별도 삭제 원장의 경계

삭제·별도 보존 연장·만료 행 제거를 같은 SQLite 트랜잭션의 `recovery_events`에 기록한다. 별도 파일에는 DB 식별자·사건 순번·이전 해시·검증 키 ID를 포함한 HMAC-SHA-256 연결 원장으로 전달하고 파일을 동기화한 뒤 응답한다. 실패한 업무 트랜잭션은 별도 원장에 삭제 사실을 남기지 않는다.

DB 변경이 확정된 뒤 외부 파일 전달이 실패하면 이미 확정된 DB 삭제를 취소했다고 안내하지 않는다. `RECOVERY_SYNC_REQUIRED`와 503으로 전달 확인 대기를 안내하고 일반 이용을 막는다. 전달 대기 사건을 복구한 다음 같은 요청의 상태를 확인하며 삭제를 다시 실행하지 않는다. 응답이 확인되지 않은 장애 구간과 실제 저장·전달 결과를 분리한다.

원장의 이름·연락처·비밀번호·답안 원문을 별도 삭제 원장에 복사하지 않는다. 기관·대상·접수자 ID, 삭제 작업·자료 종류별 건수와 보존 사본 식별자·해시는 포함하므로 익명 자료로 취급하면 안 된다. `READX_RECOVERY_KEYS`는 감사·개인정보·MFA·백업 키와 분리한다. 운영 원장은 절대 경로를 사용하고 운영 DB 디렉터리·공개 소스/산출물에서 분리한다. 단순히 다른 디렉터리에 둔 것을 다른 장치·국내 보관·변경 방지 저장소의 검증으로 주장하지 않는다.

원장 누락·잘림·변조·기관/DB 불일치와 DB보다 앞선 삭제 이력은 서비스 재개를 막는다. 별도 보관한 서명 기준점도 검증한다. 알려진 기준점 이후의 전체 이력 보존과 관리자의 키·저장소 접근까지 자동으로 보증하는 체계는 아니므로 실제 외부 보관·기준점 갱신·점검이 필요하다.

## 격리 복원과 자료 재처리

검증한 과거 DB에 별도 원장의 삭제를 재적용하여 대상의 계정 비밀, 학습·시험·파일럿·출결·상담·동의·연결·이전 권리 자료를 다시 제거한다. 다른 학생의 자료는 보존한다. 후속 만료 파기 사건에 해당하는 별도 보존 사본도 다시 제거한다. 운영 자료 삭제와 복원 재처리는 같은 제거 함수를 사용한다. 새 저장 표의 삭제 기준이 빠졌으면 검토 전 재처리를 거절한다.

별도 보존 사본의 최신 메타데이터·본문 해시와 암호화를 확인한다. 백업에 필요한 사본이 없거나 보존 연장 전의 오래된 사본만 있으면 복구 완료로 처리하지 않는다. 해당 자료가 있는 검증 백업 등 실제 복구 근거가 필요하다. 삭제 원장은 사본 본문을 보유하지 않으므로 없는 사본을 만들어 내지 않는다. 실제 보존 사본의 복제·백업 주기와 복구 목표를 운영에서 충족해야 한다.

복원 중에는 `.restore.pending`으로 서비스 시작을 막는다. 원장 재처리·DB 무결성·접속기록 검증·SQLite 정리가 끝나야 표식을 해제한다. 실패하면 격리를 유지한다. 이미 사용 중인 DB를 백업 파일로 덮어쓰지 않고 새 경로에 복원한다. 같은 삭제 원장에 연결된 원본과 복원 DB를 동시에 서비스하는 것도 활성 서버 잠금으로 제한한다. 현재 단일 서버 프로세스 운영 경계이며 분산 잠금·다중 서버 고가용성을 검증한 결과는 아니다.

## 복원된 인증과 보호자 관계

과거 백업의 세션·복구 코드·기기 키를 회수한다. 삭제되지 않은 복원 계정도 `restoreCredentialHold`로 일반 기록 접근을 막는다. 실제 본인·현재 재직/담당 범위·이용 자격·보호자 관계를 확인한 뒤 발급한 새 코드로 이전과 다른 비밀번호를 정해야 한다. 일반 비밀번호 변경이나 계정 편집으로 이 확인을 우회하지 못한다.

이전 인증앱은 복구 필요 상태로 바꾸고 이전 일회용 MFA 복구 코드를 무효화한다. 새 비밀번호 확인과 별도의 본인 확인에 따른 서버 MFA 복구·새 인증앱 등록 뒤에 접근한다. 이전 MFA 암호문을 물리적으로 전부 파기했다는 뜻은 아니다. 보호자 확인은 복원 후 재확인 대상으로 돌리고 기존 연결·동의를 그대로 학습 이용 권한으로 재사용하지 않는다.

복원 계정 안내·코드 입력 화면과 원장의 복원 계정 확인 근거 입력을 연결했다. 실제 신원이나 법정대리인 관계를 소프트웨어가 자동 인증했다고 주장하지 않는다.

## 암호화 백업과 만료 파일 처리

SQLite 스냅샷 API로 일관된 이미지를 만들고 AES-256-GCM으로 파일을 암호화한다. `READX_BACKUP_KEYS`는 다른 검증·암호화 키와 분리한다. DB/백업 식별자, 보존 종료 시각, 원장·접속기록 기준점, 이미지 해시와 크기를 인증된 머리글에 묶는다. 백업 전체 해시와 키·태그·이미지 해시·DB 무결성을 확인하며 인증이 끝나기 전 SQLite로 열지 않는다. 변경된 파일·틀린 키·잘린 봉투·다른 해시는 사용 가능한 복원 DB를 만들지 못한다.

검토 문서와 미래 보존 종료일이 있어야 백업한다. 종료일이 지난 파일은 일반 복원 경로로 재사용하지 않는다. 만료 파일 제거는 검증된 해시·키·대상 DB·보존 종료를 확인한 후 준비 사건을 먼저 별도 원장에 기록하고 파일을 제거한 뒤 결과를 남긴다. 제거 직후 장애가 난 경우 준비 기록으로 결과를 재확인할 수 있게 했다. 다른 이름으로 다시 나타난 같은 만료 파기 백업 ID도 복원하지 않는다.

백업·복원·기준점 파일을 기존 파일 위에 덮어쓰지 않는다. 작업 파일은 전용 비공개 단계 디렉터리에 두고 정상/처리 가능한 오류 경로에서 정리한다. 암복호화 과정에는 일시적인 평문 SQLite 이미지가 있으므로 DB와 단계 디렉터리의 암호화 볼륨·권한·강제 종료 후 잔여 파일 점검이 필요하다. 파일 제거·WAL 비움·`fsync`를 SSD·파일시스템 스냅샷·모든 백업 사본의 물리적 파기 인증으로 표현하지 않는다.

현재 한 백업 이미지는 16GiB, 별도 삭제 원장은 64MiB 경계를 둔다. 초과하면 분리·아카이브·운영 검토가 필요하며 법적 보유·삭제 권리를 이 숫자로 제한하면 안 된다. 자동 주기 실행·외부 복제·용량·실제 복구 시간은 운영 환경에서 별도 검증한다.

## 유지보수·이관·공개 산출물

유지보수 잠금으로 같은 버전의 서버 API·시간 만료 처리와 로컬 계정 관리의 쓰기를 중지한다. 진행 중 DB 쓰기가 끝났는지 확인한 뒤 `secure_delete=ON`, WAL checkpoint, VACUUM과 무결성 검사를 수행한다. 다른 읽기 연결이 WAL 정리를 막으면 완료 결과를 내지 않는다. 유실한 과거 소프트웨어 프로세스나 임의의 외부 DB 작성자까지 통제하는 운영망 격리를 구현한 것은 아니므로 구버전 종료·배포 절차가 필요하다.

이전 버전에서 삭제한 계정은 암호화한 원본 요청·실제 제거 상태를 확인하여 명시적으로 이관한다. `adopted_existing`과 현재 이관 시각·근거를 남기며 과거 시점에 이미 서명된 별도 원장이 있었다고 꾸미지 않는다. 필요한 원본·보존 자료가 없으면 이관을 거절한다.

운영 DB·키·복구 파일을 공개 소스/산출물에 두지 못하게 하고 동기화 제외와 공개 파일 검사를 보강했다. 이름을 바꾼 SQLite/암호화 백업, 키 구성과 기준점·잠금 자료도 검사한다. 이는 정해진 형식과 경로에 대한 검사이며 모든 개인정보 내용의 자동 탐지·외부 인증을 뜻하지 않는다.

## 운영 전환에서 남은 부분

최신 별도 접속기록 기준점이 백업보다 앞서 있으면 그 이후 기록의 보전도 확인해야 한다. 현재 도구는 외부 접속기록 아카이브의 자동 병합이나 잃어버린 최신 업무 기록 복구를 완료한 도구가 아니다. 조건을 충족하지 못하면 격리를 유지한다. 전원 차단·호스트 강제 종료·국내 운영 단말·실제 장치/복구 부하·침투 검증도 남아 있다.

SQLite 동작은 [공식 PRAGMA 문서](https://www.sqlite.org/pragma.html), [WAL 문서](https://www.sqlite.org/wal.html), 스냅샷 API는 [Node.js 공식 SQLite 문서](https://github.com/nodejs/node/blob/main/doc/api/sqlite.md)를 근거로 구현 범위를 정했다. 보존·파기 근거는 기존 개인정보 운영 계획과 실제 법률 검토를 따른다. 공개 Sites는 가상 자료 체험판이며 국내 학원 운영 DB·실명·연락처를 연결하지 않는다.
