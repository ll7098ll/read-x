오래된 학습 DB 백업을 복원할 때 최신 별도 접속기록 기준점이 앞서 있으면 서비스를 열 수 없었다. 이제 원래 서명·순서를 유지한 접속기록 전체 보관본을 암호화해 만들고, 격리 복원 중 누락된 이후 기록을 검증하여 병합한다. 최신 보관본이 없을 때의 차단은 유지한다.

## 구현

- `webapp/server/access-archive.mjs`: 원래 접속기록 행과 서명된 기준점만 저장한다. 계정·비밀번호·답안·상담 본문을 업무 DB에서 함께 내보내지 않는다. 기록 자체의 계정 ID·접속지 등은 여전히 보호할 개인정보다.
- AES-256-GCM, 매번 새 IV, 형식 머리글을 포함한 AAD, 별도 파일 SHA-256과 원래 HMAC 연쇄를 함께 검사한다. 기존 독립 `READX_BACKUP_KEYS`를 암호화에, `READX_AUDIT_KEYS`를 원래 기록 검증에 사용한다. 과거 키 ID도 검증한다.
- 보관본은 새 경로에만 생성하고 임시 암호문을 fsync한 뒤 게시한다. 평문 보관 파일은 만들지 않는다. 검토 문서 번호·실제 미래 보존 종료일이 필요하다. 보존 종료일이 지난 보관본은 일반 복원에서 사용하지 않는다.
- 생성 시도의 문서·보관본 ID·종료일은 `local/access-archive.prepare`의 202 기록으로 남는다. CLI 성공 반환·별도 보관한 파일 해시가 실제 생성 완료 영수증이다. 준비 기록만으로 완료를 판정하지 않는다.
- 격리 복원은 보관 파일의 해시·GCM 인증·DB 식별자·행별 HMAC·순서·공통 앞부분·색인·별도 기준점을 모두 확인한다. 기존 행을 덮어쓰거나 새 서명으로 과거 기록을 다시 만들지 않는다. 추가 행과 대상 색인은 함께 트랜잭션으로 반영한다.
- `recovery-maintenance.mjs --action replay`와 `encrypted-backup.mjs --action restore`에 `--access-archive`와 `--access-archive-sha256`를 연결했다. 기준점 없는 병합은 거부한다. 오류 시 `.restore.pending`을 유지하고 삭제 재적용·계정 재확인 절차를 우회하지 않는다.
- 운영자 화면에 기간별 점검 자료와 복원용 전체 보관본의 관리 범위를 안내했다. 공개 산출물 검사에는 파일명을 바꾼 암호화 보관본과 임시 파일도 포함한다. Site 소스 복사는 보호 확장자를 대소문자 구분 없이 제외한다.
